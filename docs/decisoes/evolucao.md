# Decisões da evolução (G-01 a G-06)

Data: 14/10/2026. Registro das decisões tomadas na evolução de autenticação e sessão, cadastro de usuários, resumo do cliente, validação de documento, desconto com alçada e endurecimento da sessão. Uma linha por decisão; o motivo fica na própria linha.

## Lacunas tratadas

| ID | Lacuna | Pacote |
| --- | --- | --- |
| G-01 | Desativar usuário ou trocar papel não derruba as sessões abertas | WP-EVO-2 |
| G-02 | Contador de falhas de login gravado por leitura-modificação-gravação, perdendo incremento em tentativas paralelas | WP-EVO-1 |
| G-03 | Não há cadastro de usuários, desbloqueio manual nem troca de senha | WP-EVO-2 |
| G-04 | Desconto manual com alçada por papel | WP-EVO-5 |
| G-05 | Resumo do cliente (indicadores) para a tela de perfil | WP-EVO-3 |
| G-06 | A documentação citava Testcontainers, mas a integração usa PostgreSQL descartável do Docker Compose | WP-EVO-7 |

## Decisões

| ID | Decisão |
| --- | --- |
| D-EVO-01 | Os pacotes formam uma pilha linear (WP-EVO-1 → 2 → … → 7): todos mexem no mesmo contrato v5, na sequência de migrações, na matriz de acesso e neste arquivo. Cada PR aponta para a `main` e diz de qual PR depende; enquanto o anterior não entra, o diff inclui o dele. |
| D-EVO-02 | G-02: o contador continua zerando quando a conta é bloqueada (comportamento do CT-AUTH-101). O UPDATE atômico só incrementa se a conta não estiver bloqueada no instante do `Clock`, então tentativas durante o bloqueio não o prolongam e o bloqueio dispara uma única vez. O CT-SEC-120 verifica isso: 10 falhas paralelas resultam em conta bloqueada, 1 `ACCOUNT_LOCKED` e 10 `LOGIN_FAILED`. |
| D-EVO-03 | G-02: o login de sucesso também grava por UPDATE só das colunas de contador, bloqueio e último acesso, em vez de salvar a entidade inteira. Assim um login simultâneo não desfaz uma troca de papel ou uma desativação feita por outra requisição. |
| D-EVO-04 | G-01: o `SessionVersionFilter` confere a conta em toda requisição autenticada que tenha sessão HTTP; a API não tem outro mecanismo de login (sem token, sem Basic, sem "lembrar-me"). O `user()` do MockMvc também grava o contexto numa sessão, então os testes que usam principal sintético (`AccessMatrixTest`, `ErrorContractTest`) criam as duas contas no banco com os mesmos ids (`support/SyntheticAccounts`). |
| D-EVO-05 | Política de senha: máximo de 72 caracteres e 72 bytes UTF-8, no lugar dos 128 do plano, porque o BCrypt usa só os primeiros 72 bytes (o login já limita a 72). O mínimo de 12 vale para senha nova; o login continua aceitando 8, para não trancar contas existentes. |
| D-EVO-06 | O GERENTE não redefine a própria senha por `/users/{id}/password-reset` (409 `SELF_CHANGE_FORBIDDEN`): sem a senha atual, uma sessão roubada tomaria a conta. A própria senha muda em `PUT /auth/password`. A redefinição também desbloqueia a conta. |
| D-EVO-07 | Senha atual errada em `PUT /auth/password` conta para o bloqueio, como no login, e o serviço devolve vazio em vez de lançar exceção, para o incremento ser gravado. Se essa falha bloquear a conta, as sessões do usuário são encerradas (quem tenta adivinhar a senha atual numa sessão aberta perde a sessão). O bloqueio pelo login não encerra sessões, para que uma pessoa de fora não derrube a sessão de outra. |
| D-EVO-08 | O último GERENTE ativo é protegido só pelo gatilho `keep_one_active_manager`, sem pré-verificação duplicada no serviço. O serviço roda `SET CONSTRAINTS ... IMMEDIATE` para o 409 `LAST_MANAGER` sair na própria requisição, e o gatilho usa trava consultiva para serializar a verificação. Pela API isso só acontece em corrida (dois gerentes se rebaixando ao mesmo tempo), coberta pelo CT-USR-103. |
| D-EVO-09 | Fluxo do contrato v5: operação `planned` fica fora da comparação estrutural ao vivo e da conferência com a matriz, porque ainda não tem rota; a linha da matriz entra no mesmo commit da rota. Todo o v4 é `implemented`, então nada afrouxa para o que já existia. O relatório ao vivo passa a `reports/contrato/live-v5/`. |
| D-EVO-10 | Áreas: o GERENTE ganha USUARIOS (menu Usuários); com senha provisória, `areas` traz só TROCAR_SENHA e o frontend leva para `/conta/senha`, que fica fora do grupo das áreas para não entrar em laço de redirecionamento. |
| D-EVO-11 | As leituras para alteração de usuário travam a linha com `FOR NO KEY UPDATE`: o `audit_event` é gravado em transação própria e sua FK para `app_users` pede trava de chave compartilhada, que `FOR UPDATE` bloquearia (impasse entre a transação externa e a da auditoria). |
| D-EVO-12 | Conforme o plano: editar nome e e-mail não encerra sessões; desbloqueio não pede motivo; não existe DELETE de usuário (desativar substitui apagar). O 403 por CSRF continua com `code` `FORBIDDEN` (o plano citava `CSRF_INVALID`, que não existe no contrato). |
| D-EVO-13 | DEC-ERP-07 ("gestão de usuários fora do escopo; contas do seed") deixa de valer: o cadastro de usuários entra no contrato v5 (RF-24). O primeiro GERENTE continua vindo do seed demo ou da configuração; não há autocadastro. |
| D-EVO-14 | G-05: `v_cliente_resumo` (V9) tem grão cliente × vendedor e segue a regra do faturamento (venda = pagamento `APPROVED`, valor = itens menos desconto, estorno pela tabela `refund`). O serviço soma a loja toda para o GERENTE ou filtra o vendedor da sessão para o VENDEDOR. |
| D-EVO-15 | Escopo do resumo: contagens (pagos, pendentes, cancelados), datas e produtos mais comprados valem para a loja toda nos dois papéis (não são dado sensível); total, ticket médio e formas de pagamento seguem o escopo (`STORE` ou `OWN`); `refundsTotal` só para o GERENTE. O ticket médio divide o total do escopo pelos pedidos pagos do mesmo escopo. |
| D-EVO-16 | A tela de perfil ganhou indicadores, abas (Pedidos, Produtos mais comprados, Dados cadastrais) e "Nova venda para este cliente" (`/vender?cliente=ID`, cliente pré-selecionado e trocável). Filtros de período e situação no histórico ficam para depois: exigem parâmetros novos em `GET /customers/{id}/orders`, fora do corte mínimo. |
| D-EVO-17 | CNPJ alfanumérico suportado: a Receita emite CNPJ com letras para novas inscrições desde 31/07/2026, e o CHECK `^[0-9]{14}$` da V5 impedia a loja de cadastrar essas empresas. A V10 troca o CHECK por `^[0-9A-Z]{12}[0-9]{2}$` (os numéricos continuam válidos); a API usa `@CNPJ(format = ALPHANUMERIC)` do Hibernate Validator 9.1 (módulo 11 com valor ASCII − 48), grava sem máscara e em maiúsculas; o contrato aceita só letras maiúsculas no corpo e o frontend converte antes de enviar. |
| D-EVO-18 | A validação de documento já era Bean Validation (`@CPF`/`@CNPJ` nos DTOs, violação em `details` do 400 `VALIDATION_FAILED`); não foi criada uma anotação `@CpfCnpj` própria, que duplicaria o validador da biblioteca. O contrato passou a marcar os campos com `x-constraint` (CPF, CNPJ). |
| D-EVO-19 | Unicidade de documento: `cpf` e `cnpj` já são `UNIQUE` desde a V1 (o 409 `DUPLICATE_DOCUMENT` vem dessas constraints); nenhum índice novo. Busca exata por documento: só dígitos (CPF ou CNPJ numérico) ou 12 posições alfanuméricas com pelo menos quatro dígitos seguidas de 2 dígitos; o resto continua sendo prefixo de nome. |
| D-EVO-20 | G-04: o desconto manual é rateado nos itens. `order_item.discount` passa a ser promoção + parte manual, e `order_item.manual_discount` guarda a parte manual; `orders` guarda percentual, valor, motivo e aprovador. Assim o líquido (preço × quantidade − desconto) continua igual em faturamento, metas e resumo do cliente, sem mudar o sentido de nenhuma métrica. Só o uso de promoções (`v_uso_promocoes` e a análise do mês) passa a descontar a parte manual. A sobra de arredondamento vai para o item de maior subtotal. |
| D-EVO-21 | O limite vai em `details` (`limitPercent=5.00`) no 403 `DISCOUNT_ABOVE_LIMIT`, porque o `ErrorResponse` do contrato é fechado. O VENDEDOR também recebe a própria alçada em `QuoteResponse.manualDiscountLimitPercent`, para a tela mostrar "Seu limite". |
| D-EVO-22 | `GET /discount-policy` é só do GERENTE: o vendedor não precisa da tabela (a alçada dele chega na cotação), e o campo `allowBelowCost` cairia na regra do auditor que proíbe termos de custo nas respostas do vendedor. |
| D-EVO-23 | A aprovação do GERENTE substitui o desconto manual do pedido (não soma), vale só para `PENDING_PAYMENT` e usa a alçada e a regra de custo do GERENTE; recalcula itens, total e o valor do pagamento pendente. |
| D-EVO-24 | `BELOW_COST` só é avaliado quando há desconto manual (promoções são do GERENTE) e compara com o custo médio atual de `stock_balance`; produto sem custo conhecido não barra a venda. |
| D-EVO-25 | `discount_policy` é semeada pela migração e referencia `app_users`; o `TRUNCATE ... CASCADE` dos testes e do perfil de contrato a esvaziaria. `BusinessTables.truncate` guarda as alçadas antes e as recoloca depois, sem autor. |
| D-EVO-26 | O cliente HTTP do frontend não repete mutação que voltou com 403 de regra de negócio (`DISCOUNT_ABOVE_LIMIT`, `PASSWORD_CHANGE_REQUIRED`); só repete o 403 de CSRF (`FORBIDDEN`), como antes. |
| D-EVO-27 | WP-EVO-6 (duração absoluta da sessão, prefixo `__Host-`, limitação por IP) não foi executado por decisão do responsável em 14/10/2026 e fica como trabalho futuro. |
| D-EVO-28 | WP-EVO-8 (decisão da equipe, plano v1.2): a massa Olist entra por SQL puro executado com `psql` (`07_carga_olist.sql`), não por migração do Flyway, para servir de evidência de SQL e CRUD à disciplina de Banco de Dados. O banco de demonstração publica a porta só em `127.0.0.1:5433` e continua em `tmpfs`. |
| D-EVO-29 | A carga roda dentro do contêiner do banco (o `\copy` lê os CSVs copiados para `/tmp/pacote-sql`), porque a máquina da apresentação não precisa ter `psql` instalado. Os scripts recriam a API se acharem o banco sem esquema (banco recriado sem a API). |
| D-EVO-30 | Na CI, a massa Olist é uma etapa separada do job `bd`, depois dos testes 06* (nenhum número muda). CT-DEMO-05 sobe a API no perfil demo e usa a mesma senha das contas gerada na migração; acrescentei CT-DEMO-06, que confere que o roteiro 08 roda com exatamente as três recusas esperadas. |
| D-EVO-31 | O passo da massa Olist no roteiro de demonstração (`docs/roteiro-demonstracao.md`) entra no WP-EVO-7, que reescreve o roteiro inteiro e resolve a mudança pendente do PR #21 no mesmo arquivo. Por enquanto o passo a passo está em `docs/bd/massa-demonstracao.md`. |
| D-EVO-32 | WP-EVO-9: de `A3/marca/aplicacao/frontend/` só existem `app/brand-tokens.css` e `app/icon.svg`; `logo.tsx`, `icons.tsx`, o manual em PDF e o protótipo citados na seção 6.5 não estão na pasta. O símbolo e o logo (`components/brand/logo.tsx`) foram construídos com a geometria exata do `icon.svg` (um teste unitário compara as duas) e os ícones de traço (`components/brand/icons.tsx`) com a especificação textual da 6.5: grade de 24, traço de 1,75, pontas arredondadas, seis do manual e sete derivados. Quando os arquivos do manual chegarem, substituem estes sem mudar quem os usa. |
| D-EVO-33 | O manual de marca v1.0 substitui os tokens "SBI v1.1" do WP-3.12: `brand-tokens.css` é importado antes de `globals.css`, que perdeu o `:root` e os tamanhos de título conflitantes. Os nomes antigos (`--bg`, `--card`, `--muted`, `--primary`, `--radius`) continuam como apelidos dos novos para não reescrever todas as telas no mesmo PR. |
| D-EVO-34 | O menu é exibido em seções (GESTÃO, ATENDIMENTO, MEU ESPAÇO) com ícone e texto, mas a tela inicial depois do login continua seguindo a ordem antiga de `MENU` (o gerente segue entrando em Vender e o vendedor também): mudar o destino do login não era pedido e mudaria os testes de sessão. "Trocar senha" (`/conta/senha`) entra fixo em MEU ESPAÇO e substitui o botão "Minha senha" do rodapé. |
| D-EVO-35 | Dado ausente vira "Não informado" nos formatadores (`money` e `formatPercent` com nulo) e nos campos de detalhe; células de tabela montadas com "—" explícito continuam assim, pela densidade. KPI sem valor sai em texto (Space Grotesk), não na fonte de números. Hora no formato "14h30" em todas as telas (`formatTime` e `formatDateTime`). |
| D-EVO-36 | Abaixo de 760 px a barra lateral vira faixa superior com o símbolo de 30 px e um botão "Menu" de 44 px que abre e fecha a navegação e a fecha ao trocar de tela. A página 404 da marca só aparece com sessão aberta: sem cookie, o `proxy.ts` leva qualquer rota interna para `/entrar`, como antes. |
| D-EVO-37 | As capturas de `reports/marca/` vêm da stack `sbi-demo` (seed demo mais massa Olist, nomes fictícios), em 1280 × 800 e 390 × 844, com axe WCAG 2.2 AA em cada rota (`index.json`). |
| D-EVO-38 | G-06, decisão da equipe em 14/10/2026 (opção A da seção 8 do plano): o projeto não usa Testcontainers e não vai migrar. Os testes de integração e de contrato rodam no PostgreSQL 18 descartável via Docker Compose (`docker-compose.test.yml`, porta 15432), e a CI usa o mesmo PostgreSQL 18 como serviço. As menções a Testcontainers foram trocadas no plano de testes, nos requisitos e em `decisoes/stack.md`; README, arquitetura, plano de qualidade e relatório final passam a usar a mesma frase. O manual (`docs/referencias/Manual-Projeto-A3.md`, versão vigente) recebeu a mesma troca por decisão do responsável, junto com a nova redação da orientação de revisão de código (linha 545); o PDF é a cópia histórica de 26/09 e continua citando Testcontainers, como avisa `docs/referencias/README.md`; o plano de 07/10 em `docs/gestao/` fica como registro do que se pensava na data. |
| D-EVO-39 | Roteiro de demonstração (WP-EVO-7): reescrito para 12 minutos com a massa Olist, o desconto com alçada, a queda da sessão ao desativar um vendedor e o último gerente. Inclui a correção do PR #21 (SKU de exemplo `CG-20W` com o total esperado e o job `bd` lido na `main`), para que o conflito entre os dois PRs no mesmo arquivo se resolva ficando com esta versão. O último gerente é mostrado de duas formas, porque pela tela o gerente não tem ação sobre a própria conta: a linha "(você)" sem ação e o gatilho no IntelliJ com `SET CONSTRAINTS ALL IMMEDIATE` (o gatilho é adiado para o commit; sem a instrução, o `UPDATE` dentro de `BEGIN ... ROLLBACK` não dispara o erro). |
